# AGENTS.md

This file defines the project-scoped rules, workflows, commands, and architecture details for AI agents working in the OpenWhisperer repository.

## Commands

All Swift commands run from the `app/` directory (it's the SwiftPM package root).

```bash
cd app
swift build                                           # debug build
swift build -c release                                # release build
OW_SIGN_IDENTITY="OpenWhisperer Dev" ./build-dmg.sh   # build signed bundle + .dmg for local dev (keeps TCC grants)
./build-dmg.sh                                        # build ad-hoc bundle + .dmg (release) into app/.build/

swift run OpenWhispererKitTests      # pure-logic unit tests (exits non-zero on failure)
swift run HookTests                  # bash-hook integration tests (stubbed curl + temp HOME)

swift run OpenWhisperer --serve-tts  # headless TTS server on :8000 (no GUI) for curl/CI; TTS_PORT overrides
```

Manual TTS smoke checks (server must be running, GUI or `--serve-tts`):

```bash
curl http://localhost:8000/v1/models
echo "hello" | scripts/speak.sh
```

### Testing notes

- This machine has **Command Line Tools only, no full Xcode**, so there is **no XCTest/swift-testing**. Both test targets are plain `@main` executables that aggregate `*Failures() -> [String]` check groups and `exit(1)` if any fail. There is **no per-test filter** — to narrow a run, comment out check-group calls in the runner (`Tests/OpenWhispererKitTests/SubmitTriggerTests.swift` or `Tests/HookTests/main.swift`).
- Only **pure logic** (no AppKit/AVFoundation/WhisperKit/FluidAudio) is unit-testable, and it lives in the `OpenWhispererKit` target precisely so it builds fast under CLT. Put new testable logic there.

## Working on changes

The loop this repo already follows. The parent checkout stays on `main`; feature branches live **only** under `.claude/worktrees/` — never branch in place.

Pick the lightest safe path:

- **Local (commit straight to `main`, no PR)** — docs/CLAUDE.md/comment edits, or a small, self-contained, low-risk code fix where a PR adds ceremony without safety. Stay on `main`, make the smallest edit, verify (readback for docs; the test targets for code), commit, push. If it unexpectedly grows beyond small/isolated, switch to the PR path before committing.
- **PR** — multiple files, real logic, a dependency change, or user-visible behavior:
  1. **Worktree off `main`:** `git worktree add .claude/worktrees/<slug> -b <slug>` (or `EnterWorktree` in Claude Code).
  2. **Build + test** from `app/`: `swift run OpenWhispererKitTests` and `swift run HookTests` (both `exit(1)` on failure). For a packaged `.app`/`.dmg`, use `OW_SIGN_IDENTITY="OpenWhisperer Dev" ./build-dmg.sh` locally so TCC grants survive the rebuild (see Conventions).
  3. **PR:** rebase onto `origin/main` if it moved, push, `gh pr create`.
  4. **After merge:** sync `main` (`git pull --ff-only`), `git worktree remove .claude/worktrees/<slug>`, delete the branch. Leave no orphaned worktree dir — a stale bundle holding `:8000` is a known foot-gun.

### Commit messages

Conventional Commits, matching the existing history: `type(scope): subject`, where `type` ∈ `feat|fix|refactor|docs|test|build|chore` and `scope` is optional (commonly `tts`/`voice`/`sign`). Imperative mood; lowercase is fine for proper nouns and acronyms. Aim for a ~50-char subject, **hard cap 72 including the `type(scope):` prefix**; add a body only when the change needs a *why*, wrapped at 72. No `Co-Authored-By`/tool attribution in the message (Claude-authored commits carry only a `Claude-Session:` trailer).

## Architecture

### Targets (`app/Package.swift`)

- **`OpenWhispererKit`** — pure, dependency-free, fast-to-test logic: `SentenceSplitter`, `NumberNormalizer`, `SubmitTrigger`, `VoiceSignal`, `VoiceMigration`, `PCMConversion`, `DisfluencyFilter`, `TTSVoiceRouter`, `STTLanguages`, `TTSSampleText`.
- **`OpenWhisperer`** — the executable (AppKit/SwiftUI menubar app + native STT/TTS). Depends on `WhisperKit` (STT, upstream `argmaxinc` from 1.1.0) and `FluidAudio` (Kokoro TTS). The fork pin was dropped 2026-09-02 once argmaxinc shipped PR #514 in v1.1.0 — see `Package.swift` for what it was guarding and why `hakanensari/WhisperKit`'s `main` is a downgrade, not an upgrade.
- **`OpenWhispererKitTests`**, **`HookTests`** — the two executable test runners above.

Entry point `OpenWhispererMain.main()`: `--serve-tts` → headless TTS; otherwise the SwiftUI `MenuBarExtra` app. `AppDelegate` owns the long-lived managers (`ServerManager`, `SetupManager`, `DictationManager`, `HotkeyManager`, `AccessibilityManager`). The app is `LSUIElement` (menubar only, no dock icon).

### STT (dictation) — fully in-process, no server

`HotkeyManager` watches a modifier key (Ctrl/fn/Option/Cmd) → `AppDelegate` captures the frontmost app's PID *before* any focus shift → `DictationManager` orchestrates: `AudioRecorder` (16 kHz mono PCM) → `SpeechTranscriber` (WhisperKit large-v3 turbo, on the ANE) → types the result into the captured app via Accessibility / CGEvent Unicode (the **clipboard is never touched**). Three `InteractionMode`s: `holdToTalk` (default), `pressToTalk`, `handsFree` (`KeywordDetector` uses Apple's Speech framework for "initiate"/"hold on").

> **AX writes are verified, not trusted (2026-09-20, #49).** `AXUIElementSetAttributeValue` returning `.success` means the app accepted the message, not that it applied it. iTerm2 accepts a `kAXValue` write and silently discards it, so `insertViaAccessibility` reported success and the CGEvent Unicode fallback — the path that works there — never ran; the Auto-Submit Enter still landed, so the user got an empty command submitted. Terminal.app only ever "worked" because its write fails honestly. Both strategies now read `kAXValue` back and compare against a baseline taken before the write, via pure `AXInsertionCheck` (Kit, unit-tested). It is **deliberately biased toward trusting the write**: it reports failure only when the value is readable at both ends and byte-identical, because a false negative types the sentence twice, which is worse than the bug. Unreadable either side, or changed in a way we can't attribute (a terminal repainting), counts as inserted. Not reproduced locally — no iTerm2 on this machine — so the log lines name which branch was taken.
>
> **STT is WhisperKit again since 2026-07-30** — the owner reversed the 2026-07-13 Parakeet migration and asked for WhisperKit back; `ParakeetTranscriber` is deleted and `SpeechTranscriber` restored. **Do not "re-optimize" this back to Parakeet** — it is a deliberate owner decision made with the measurements in front of them.
>
> What that trade costs, from the 2026-07-13 A/B (kept here so nobody re-derives it): Parakeet decoded ~8–10x faster (50–80 ms vs 500–900 ms per clip) and cold-loaded in ~12 s vs ~96 s. What it buys: Whisper's stronger noise robustness, ~99 languages vs ~25, and polished output (it edits fillers/casing rather than transcribing literally). Full evidence: `docs/superpowers/specs/2026-06-20-engine-configurability-design.md`. A side-by-side trade-off write-up lives on the unmerged `whisperkit-vs-parakeet` branch (PR #34) — not on `main`.
>
> **Language roster + default (2026-08-01).** Settings → Dictate offers **all 100** codes WhisperKit accepts (`STTLanguages` in Kit, intersected with `Constants.languageCodes` so the UI can only shrink toward what the decoder knows), split into three tiers — **good** (≤35% error, 56), **limited** (>35%, 9, each badged with its own number), **untested** (no published benchmark, 35). The rates come from OpenAI's published `language-breakdown.svg` for large-v3 (Common Voice 15 + FLEURS, better of the two); the full table and how it was decoded live in `docs/superpowers/specs/2026-08-01-full-language-rosters-design.md` — **don't re-derive them**. Nothing is hidden: the tiers set expectations, they don't gate. The default is now **English**, not Auto-detect (`ConfigManager.migrateDefaultSTTLanguage()` writes `en` when nothing is stored) — detection costs a decoder pass and is least reliable on short clips, and the owner measured fewer errors with English pinned. **Do not restore Auto-detect as the default**; it remains an explicit choice.
>
> `stt_vocabulary` now feeds **both** layers: acoustic `promptTokens` (`VocabularyPrompt` in Kit, Whisper-only, budgeted) and the post-transcription fuzzy `VocabularyCorrector`. `DisfluencyFilter` (2026-07-17) still runs post-transcription; it was written for Parakeet's literal transcripts and is mostly a no-op on Whisper output, but is harmless. The transcription watchdog is 35 s warm / 180 s cold — a cold first dictation loads the model inside the watchdogged task, and recording-start pre-warms it.

### TTS (spoken replies) — in-process synth + playback, `speak` MCP tool

`ServerManager` hosts `TTSEngines` (FluidAudio) behind `TTSHTTPServer`, a tiny loopback-only HTTP/1.1 server on **:8000** (Network.framework, zero deps). The app also hosts a minimal **MCP server at `POST /mcp`** exposing a `speak` tool (see Voice-turn handshake): the model calls `speak(text, voice?, speed?)` mid-turn (optional `voice`, resolved from the user's `tts_voice` pref, and `speed`, clamped via `TTSSpeed`, both defaulting to the user's global prefs) → the in-process `MCPServer` dispatch (`OpenWhispererKit`, pure JSON-RPC) → `TTSPlaybackController` synthesizes **sentence-by-sentence** (`SentenceSplitter`) and plays gaplessly via `AudioPlaybackEngine` (`AVAudioPlayerNode`) — so the first sentence plays while the rest are still synthesizing. Endpoints: `GET /v1/models`, `POST /v1/audio/speech` (blocking WAV — used by `scripts/speak.sh`), `POST /v1/audio/play` (fire-and-forget; also takes optional `voice` (resolved from `tts_voice`) and `speed` (clamped via `TTSSpeed`); used by the Pi extension's `openwhisperer_speak` tool), `POST /mcp` (MCP Streamable HTTP, protocol `2025-11-25` — the `speak` tool).

**Playback rate.** The global `tts_speed` pref (a Settings → Voice slider, 0.7–1.5, default 1.1 — upstream is 1.0) is threaded into `KokoroTTS` synthesis and read where `tts_volume` is read — `TTSPlaybackController` (so the `speak` tool + `/v1/audio/play` pick it up) and the blocking `/v1/audio/speech` (which also honors an optional per-request `speed`). Parsing/clamping lives in pure `TTSSpeed` (`OpenWhispererKit`), unit-tested; its `[min, max]` MUST stay equal to the Settings → Voice `Slider`'s `in:` range.

**The analyzer spectrum is gated (2026-09-06).** Both audio taps — mic input (`AudioRecorder`) and TTS output (`AudioPlaybackEngine`) — reduce every buffer to 96 `SpectrumBands` energies on a real-time render thread. Only three of the four overlay styles draw them: the default `.wave` reads `levelHistory` instead. `SpectrumGate.isEnabled` (app target, `nonisolated(unsafe)`, main-thread writes, unsynchronized reads by design) skips that analysis unless the overlay is visible **and** `OverlayStyle.usesSpectrumBands`. It gates *only the filterbank*: the mic tap still computes RMS and publishes `audioLevel`/`levelHistory` every callback, because the always-on `.wave` style needs them.

Why: on default settings the filterbank ran on every buffer of both taps and the result was discarded — ~0.5 ms per 2048-frame buffer, ~0.12 ms per 512-frame mic buffer (measured, `-O`).

**Measured on hardware 2026-09-06, and it is smaller than it looks — do not re-sell this as a CPU win.** An A/B of 2.0.4 vs 2.0.5 on an M-series Air found *no* idle drain after playback (0.08% vs 0.03% of a core) and no measurable saving during playback (14.9% vs 15.7%; 2.0.5 is marginally higher because the Speaking indicator now updates instantly rather than up to 300 ms late, so the overlay animation runs slightly longer). An earlier claim of "~1% of a core forever after the first spoken reply" was **wrong**: it inferred continuous rendering from an `enableManualRenderingMode(.offline)` probe, but `renderOffline` *forces* the graph to render. In real time, with no player node playing, the engine does not pull and the tap does not fire — so there is nothing to skip while idle. Taps genuinely are not skipped for *silent* buffers, but that only matters while something is actually rendering. The gate is still correct (it removes provably dead work) and the mic-tap case during dictation is untested; just don't quote an idle-CPU number for it.

**The real cost in this area is the overlay, not the taps:** `WaveStyleView`'s "Speaking…" animation is a 33 fps `TimelineView` and measures ~15% of a core while a reply plays — an order of magnitude more than the filterbank — and it runs *indefinitely* if playback never drains (see the playback-drain watchdog note under TTS).

**`TranscriptionOverlay` is the gate's sole writer** — it encodes "does anyone need bands?" as "is the overlay visible on a band-drawing style". Retiring or replacing the overlay (e.g. `docs/superpowers/plans/2026-07-13-notch-status-indicator.md`, which deletes it — and whose sample code still polls `tts_playing.lock`, which this section now forbids) silently blanks every analyzer style with no build or test failure. A second *simultaneous* consumer must convert this to a demand count, not add a second writer. `OverlayStyle.usesSpectrumBands` is an exhaustive `switch` and is also enumerated over `allCases` in `OverlayStyleChecks`, so a new style is a compile error first and a test failure second.

**Playback drain watchdog (2026-09-06).** `AudioPlaybackEngine.schedule` only reports completion through `.dataPlayedBack`, which requires the output device to *actually render*. With an aggregate / multi-output device whose member is disconnected, `engine.start()` succeeds and nothing plays: `pending` never returns to zero, `onDrained` never fires, the item never finishes, `tts_playing.lock` is never removed, and the overlay's "Speaking…" animation runs for the life of the process (~12% of a core — observed live on a "Multi-Out BT" device). `TTSPlaybackController.synthFinished` now arms a watchdog for the scheduled audio's own duration plus a 10 s grace; on expiry it stops the engine (resetting `pending`, so the next utterance isn't queued behind a count that will never clear), clears the queue and releases the lock. The grace is deliberately generous — firing early would truncate a reply, while the failure it catches is permanent, so being late costs nothing. **Verified not to misfire on normal playback; the recovery path itself is untested on hardware** (it needs a non-rendering output device to reproduce).

**Overlay redraw cost (2026-09-06).** `WaveStyleView` draws with `Canvas`, not `Shape.fill`, and its speaking animation runs at `speakingFrameInterval` (0.05 → 20 fps), not 30. Both branches redraw constantly — the speaking wave for the whole reply, the recording wave on every `levelHistory` publish (~90/s) — and the bars are composited over the overlay's blur material, so the redraw *rate* is what this view costs. Measured while a reply played: 15.7% of a core before, 14.3% with `Canvas` alone, **11.7% with `Canvas` + 20 fps**, against a 4.1% floor with the overlay hidden — i.e. the view itself went from ~11.6 points to ~7.7. Don't raise the frame rate back without re-measuring; the wave is a decorative sine blend, not a reading of the audio. The recording branch still publishes at ~90/s and is the obvious next candidate.

**Barge-in** is in-process: starting a recording (or "hold on") calls `TTSPlaybackController.bargeIn()`, which cancels pending synthesis (freeing the ANE for STT) and stops audio instantly. `DictationManager` gets the controller injected by `AppDelegate`.

**Two engines behind one hub (2.0.0).** Kokoro-82M has no voice for Dutch/German/Polish/Russian/… — it renders them as an English voice reading foreign text, which is *unintelligible*, not merely accented (a Dutch ASR read-back of Kokoro's Dutch scores ~100% WER vs ~4% for Supertonic-3). So `TTSEngines` routes by voice id: `KokoroTTS` for its nine languages (still the default), `Supertonic3TTS` (FluidAudio's Supertonic-3, 31 languages, ANE, 44.1 kHz) for the rest. Kokoro ids stay **bare** (`af_heart`, no migration); Supertonic ids are **`supertonic:<lang>:<style>`** (`supertonic:nl:F1`). Resolution lives in pure `TTSVoiceRouter` (`OpenWhispererKit`, unit-tested); `TTSEngines` exposes the exact surface `KokoroTTS` did, so downstream (streaming, barge-in, `speak`, `/v1/audio/speech`) is untouched.

Don't re-litigate these, they were measured (see `docs/superpowers/specs/2026-07-30-multilingual-tts-supertonic3-design.md`):
- **`.aneBucketed(.int8)`, not FP16 and not the upstream `int4` default.** FP16's RangeDim shapes can't use the ANE, so it measured slower *and* off-ANE (0.67 s vs 0.12 s). int8 is "transparent" quality on the ANE. Supertonic int8 is ~10× faster than Kokoro (19.2× realtime vs 1.93×).
- **`AudioPlaybackEngine` does NOT take a per-item sample rate** — it builds one fixed 24 kHz format in `init`. Supertonic's 44.1 kHz is downsampled in `TTSEngines` (a raw 44.1 kHz buffer plays ~1.8× too slow). The WAV path keeps native rate.
- **No Mandarin in Supertonic** (untrained) — `supertonic:zh:*` deliberately falls back to Kokoro, which keeps its `z*` voices.
- **Roster is a UI decision, not a bytes decision.** All 31 languages ride in the one model, so listing one costs nothing. As of 2026-08-01 the picker shows **all 24 Supertonic languages Kokoro cannot speak** (ar/bg/cs/da/de/el/et/fi/hr/hu/id/ko/lt/lv/nl/pl/ro/ru/sk/sl/sv/tr/uk/vi × F1/M1) — widened from a curated five on owner request; **do not re-narrow it**. The seven languages both engines cover (en/es/fr/it/pt/hi/ja) stay Kokoro-only so no language appears twice and the picker never asks the user to choose an engine. The router still accepts all 31 for `OW_TTS_VOICE`. F1–F5/M1–M5 are generic speaker *styles*, not accents — there is no Flemish-vs-Netherlands choice to expose, which is why Settings has **no** language/accent control (language rides inside the id, so a separate dropdown could only produce invalid pairs). Registry group names **must** equal the names `resolve_language_line()` emits; `HookTests`' `voiceLanguageParityFailures()` asserts it across both targets.
- **The reply-language nudge is the easy-to-miss half.** `resolve_language_line()` in `hooks/voice-shared.sh` tells the model to write the `speak` text in the voice's language — without it a Dutch voice reads English. Sentinel `Write the text you pass to \`speak\` in`, kept distinct from the persona sentinel; multilingual voices get this line *instead of* a persona. Map lives only in the hook; `HookTests` guards it.

### Theming (2.0.1)

Six selectable appearances live in pure `OWTheme` (`OpenWhispererKit`): **Cream** (the original identity, the default, and the **only** theme that follows the system light/dark appearance) plus five ports of the Authé design system's palettes (`apps/authe-app/app/globals.css` — `:root`, `.dark`, `.pastel`, `.champ`, `.sky-champ`, defined in OKLCH and converted to sRGB). `ThemeManager` persists the choice to `ui_theme`, overrides `NSApp.appearance` (without it a fixed dark theme still draws light system chrome), and repaints owned windows plus the overlay faceplate.

Don't re-introduce these, they were found in review:
- **`OWColor`'s tokens are computed `var`s, never `let`.** A `static let` caches once per process, which would freeze the palette at launch. The same trap bit `WaveStyleView`'s three gradients — they were `static let` and kept drawing the old theme's colours until relaunch.
- **Anything derived from `OWColor` must be recomputed, not stored.** `CALayer` colours (the overlay faceplate) resolve immediately and need an explicit repaint — `TranscriptionOverlay.refreshTheme()`.
- **Contrast is unit-tested.** `OWThemeChecks` holds `accentDeep` on `surface` to 4.5:1 (it is link text) and `warn` on `page` to 3:1. Cream's own `accentDeep` was darkened to `0x926F3A` to clear it.

### Voice-turn handshake (nudge + `speak` tool — the subtle part)

By default (**Response = `when Voice`**) only **voice-dictated** turns are spoken; typed turns stay silent. The `tts_response_mode` pref (or per-project `OW_TTS_RESPONSE`) changes *when* replies are spoken — `voice` (default) | `always` | `needed`. **`needed` ("Only when I'm needed") cannot be decided by the hook**, which runs at prompt-submit before the turn exists and has no Stop-hook counterpart: it makes every turn a candidate and delegates the gate to the model, whose nudge says to call `speak` only when the turn ends on the user (question / blocked / approval / failure) and to stay silent otherwise. Same no-fallback trade as the rest of the handshake. There is **no Stop hook and no `speak_pending` marker**: the model's own mid-turn `speak` tool call produces the audio, so it starts ~1 s into the turn instead of after the reply finishes. The mechanism:

1. On each dictation the app writes `voice_turn` = SHA-256 of the dictated text + a unix timestamp (`VoiceSignal.canonicalHash`).
2. The **UserPromptSubmit** hook (`hooks/voice-context.sh`) recomputes `shasum -a 256` of the submitted prompt; on a match it **claims (removes)** `voice_turn`, classifies the turn `IS_VOICE`, applies the response mode, and on a "speak" decision injects a hidden `additionalContext` nudge telling the model to **call the `speak` tool first** with a standalone spoken summary (length shaped by `tts_style`).
3. The model calls `speak(text)` → the app's `POST /mcp` handler synthesizes + plays in-process. Nothing runs at turn end.

**Native-tongue flavor.** For a **personified** voice, `voice-context.sh` reads `tts_voice` and adds one layer to the nudge: an **ungated persona** — a light national character (e.g. French = *dry and faintly unimpressed*; Hindi = *irrepressibly helpful*; American English = *quietly self-assured, light SV hype*; British English = *dry and unflappable*), present on **every** turn for that voice. First-char map: `a`→American English, `b`→British English, `f`→French, `i`→Italian, `e`→Spanish, `p`→Brazilian Portuguese, `h`→Hindi, `j`→Japanese, `z`→Mandarin Chinese; unknown/no-voice gets nothing. The hook is the only thing that **steers** the model, and stays the source of truth: reword a persona in `voice-shared.sh` first. Since 2026-08-18 it has a **display-only** mirror, `VoicePersona` (`OpenWhispererKit`), so Settings → Voice can disclose the persona your voice carries — it applied on every turn and was surfaced nowhere. Nothing reads `VoicePersona` at nudge time. `HookTests` guards both: the persona sentinel `voice speaking your reply`, and `voicePersonaParityFailures()`, which parses `resolve_flavor()`'s case arms and fails on any drift in either direction (a Kit entry the hook lacks would disclose a persona the model never gets; a hook entry the Kit lacks is the original gap). Same arrangement as `resolve_language_line()` and `TTSVoiceRegistry`. Since 2026-09-02 the Pi extension carries a third copy of both maps (`PERSONAS`/`LANGUAGES` in `pi/openwhisperer.ts` — it cannot source the hook), guarded the same way by `piNudgeParityFailures()`; all three checks share one parser, `VoiceSharedMaps`. **Why this shape (don't re-litigate):** the personas are a deliberate, *playful* national-stereotype touch kept subdued — personality only, no vocabulary steering. An earlier cut also had a rare-gated "native word" line (`OW_FLAVOR_ROLL`, ~1 in 5 turns) plus tone-not-vocabulary guardrails; both were dropped 2026-07-02 after transcripts showed the model code-switches from the persona alone (the gate never fired, yet every spoken summary carried a foreign word), so the extra wording was dead weight. Whatever code-switching happens now is the model's own. Tune the wording in the hook, and keep it subdued.

**One hook, both platforms.** `voice-context.sh` serves Claude Code *and* Codex — both fire a `UserPromptSubmit` command hook whose stdin carries `prompt`+`session_id` and whose stdout `{hookSpecificOutput:{additionalContext}}` is honored identically. `ConfigManager` registers the MCP server + this hook for each platform (Claude → `~/.claude.json` + `~/.claude/settings.json`; Codex → `~/.codex/config.toml` + `~/.codex/hooks.json`). Both hooks files share one `{"hooks": {Event: [{"hooks": [...]}]}}` shape, and both are shared with other tools, so edits go through the pure `HooksJSON` (`OpenWhispererKit`, unit-tested) and touch only our own entries — a foreign hook in the same group survives.

`VoiceSignal.canonicalHash` lives in `OpenWhispererKit` and is unit-tested specifically to guarantee parity with the bash `shasum` reader — **if you touch hashing/trimming on either side, update both and run `HookTests`.**

**Known limitations (by design, document don't "fix" blindly):**
- The hash covers the **dictated text only**. It matches the submitted prompt **only when the input buffer was empty** before dictation. Pre-typed text in the prompt, or dictating twice into one prompt, makes `trim(prompt) != dictated text` → the turn is treated as typed and silently **not spoken**. Editing a dictated prompt before submit (manual-submit mode) likewise un-matches — which is correct (you took over by keyboard).
- **No fallback.** If the model doesn't call `speak` on a turn the mode meant to speak, that turn is simply silent (accepted, KISS). Spiked at 13/13 (Claude) and 5/5 (Codex) speak-first; the untested case is very long interactive agentic turns.
- **Codex requires hook trust.** Codex silently skips *untrusted* hooks, so a first-run user must approve trusting the OpenWhisperer hook once (the setup window says so). Until then, dictated turns are silent on Codex. Trust is keyed by file and position, so moving the hook re-prompts.
- **The Codex hook lives in `~/.codex/hooks.json`, not inline in `config.toml`** (2026-09-02, #56). Codex loads both representations but warns whenever one layer carries both, and other managed integrations already use `hooks.json`. `config.toml` keeps only the `[mcp_servers.OpenWhisperer]` table (plus whatever the user has there, `[features] hooks = true` and `[hooks.state]` included). Existing installs are migrated at launch (`ConfigManager.migrateCodexInlineHook()`) and on Connect: the pure `CodexConfigTOML` (`OpenWhispererKit`, unit-tested) lifts only our `[[hooks.UserPromptSubmit]]` tables and the legacy `notify` line out of `config.toml`, section by section, without a TOML parser — a foreign hook, even one sharing our group, stays byte-for-byte. `checkCodexHookConfigured()` reports "Connected" only in the new shape.
- The voice-turn TTL is **900 s**, uniform across `voice-context.sh` and `codex-tts-hook.sh`'s successor (none — Codex now shares `voice-context.sh`).
- **Antigravity (agy) is supported** (2026-07-06, superseding the earlier "unsupported" finding). agy's `PreInvocation` hook — undocumented in the 2026-06-29 spike, present in agy v1.0.16 — fires before every model call, and `invocationNum` resets to `0` at the start of each new user turn (confirmed live), giving early-speak the once-per-turn gate it needs. `hooks/agy-previnvocation.sh` reads the just-submitted prompt from `transcriptPath`'s last `USER_EXPLICIT` entry (no prompt text is given on stdin), classifies it against `voice_turn` via the shared `hooks/voice-shared.sh` (also used by `voice-context.sh`), and on a "speak" decision emits `{"injectSteps":[{"ephemeralMessage": "..."}]}`. The `speak` MCP tool is reached over agy's `serverUrl` (SSE) transport in `~/.gemini/config/mcp_config.json`, pointed at the same `POST /mcp` endpoint Claude/Codex/Pi use — no stdio shim needed, contrary to an earlier design review. The hook is registered in the **global** `~/.gemini/config/hooks.json`, not a per-workspace `.agents/hooks.json` (confirmed live: the global file fires for any workspace). Like Claude/Codex, there is no Stop-hook fallback — a missed `speak` call means a silent turn. See `docs/superpowers/specs/2026-07-06-agy-voice-support-design.md` for the full spike findings.
- **Pi (`@earendil-works/pi-coding-agent`) — supported via a single extension, NOT MCP** (validated 2026-06-29). Pi is deliberately MCP-free (its author, Mario Zechner, argues you often don't need MCP), so one self-contained TS extension (`~/.pi/agent/extensions/openwhisperer.ts`) replaces the MCP-server + bash-hook combo: `pi.registerTool({ name: "openwhisperer_speak" })` plays via the existing `:8000` `/v1/audio/play` endpoint, and a `before_agent_start` handler reads `voice_turn`, hash-matches the prompt (same `VoiceSignal.canonicalHash`), and injects the gated speak-first nudge — with the same persona and reply-language layers as the bash hook since 2026-09-02 (`resolveFlavor()`/`resolveLanguageLine()` mirror `resolve_flavor()`/`resolve_language_line()`; `piNudgeParityFailures()` fails on drift in either direction and runs `node --check` on the file when node is on PATH; before that Pi had neither layer, unnoticed for two months because the parity checks only compared the hook with the Kit); a `renderCall` shows a branded "OpenWhisperer" TUI header. Validated end-to-end on **Pi + local ollama `gemma4`** — free, fully offline, no cloud key (gemma4 *is* tool-capable: ollama advertises `tools`). The extension lives at `pi/openwhisperer.ts` (bundled into the `.app`); selecting **Pi** in Settings → Agents → Auto-Apply copies it into `~/.pi/agent/extensions/` (`ConfigManager.applyToPi`), then `/reload` in Pi loads it. It hits the TTS server's `/v1/audio/play` endpoint — no MCP, no bash hook, no hook-trust: the lightest of the three integrations.

### State & IPC: flat files in Application Support

`~/Library/Application Support/OpenWhisperer` (0700) is the shared bus between the GUI app, the bash hooks, and the embedded server. All prefs and signals are flat files — see `Paths.swift` for the full list. Notable ones: `tts_voice`, `tts_volume`, `tts_speed` (global TTS playback rate, default 1.1, clamped 0.7–1.5 via `TTSSpeed`), `stt_language` (dictation language; **defaults to `en`** via `ConfigManager.migrateDefaultSTTLanguage()` — a literal `auto` is the explicit opt-in to detection), `interaction_mode`, `ptt_hotkey`, `tts_style` (spoken-summary length: `terse`/`normal`/`rich`/`full`; `full` is its own longest tier again as of 2.0.0 — a spoken paragraph plus a `resolve_depth_line()` explain-the-reasoning instruction — having previously folded into `rich`, so a legacy stored `full` is promoted rather than capped; was `voice_detail` before the rename — `ConfigManager.migrateVoiceDetailToTtsStyle()` migrates it on launch), `tts_response_mode` (when replies are spoken: `voice`/`always`), `selected_platform`, `auto_submit`, `auto_focus_app`, `voice_turn`, and `tts_playing.lock` (written while speaking). **Nothing outside this process reads `tts_playing.lock`** — not the hooks, not the Pi extension, not `scripts/`. It is written for the documented bus, but since 2026-09-06 the app learns its own playback state from the in-process `TTSPlaybackState` (`@Published`, set by `TTSPlaybackController.writeLock/removeLock` and by `DictationManager.killTTS`) instead of polling the file back off disk from two places. That makes the file **write-only and best-effort** — nothing corrects it any more, so it can survive a crash mid-utterance, and `ConfigManager.cleanTempFiles()` deletes it a second after launch. `TTSPlaybackState` is the only source of truth: don't reintroduce a poll, and don't add a reader (a cross-platform port included) without first making the write authoritative. Subscribers must use `.receive(on: DispatchQueue.main)`, not `RunLoop.main`, which delivers in the default run-loop mode only and would drop the hands-free mic mute while a menu is tracking.

These are global (one menubar setting for all repos), but `tts_style`, `tts_response_mode`, `tts_voice`, `tts_speed`, and `tts_persona` can be **overridden per-project** via env vars in that repo's `.claude/settings.local.json` `env` block — read by `voice-context.sh` (and Pi's extension), which take precedence over the global files: `OW_TTS_STYLE`, `OW_TTS_RESPONSE`, `OW_TTS_VOICE`, `OW_TTS_SPEED`, and `OW_TTS_PERSONA`. For Claude/Codex, voice/speed overrides are injected into the speak nudge as `speak` tool args (model-echoed); on Pi the extension passes them to `/v1/audio/play` directly (deterministic). For Claude/Codex/Pi, the override voice also drives the native-tongue flavor — unless `tts_persona`/`OW_TTS_PERSONA` names one explicitly, which wins over the voice's own (`auto`, empty, and an unrecognized value all fall back to the voice). **Nothing here is per-agent.** The hooks never read `selected_platform`, so every agent shares one voice, persona, style and speed; per-*project* env vars are the only axis of variation. A persona control in Settings → Agents would imply a scoping that does not exist.

### Concurrency

`SpeechTranscriber`, `KokoroTTS`, and `TTSPlaybackController` are **actors** — they serialize work on the single ANE/compute unit and dedup the one-time model load (concurrent callers await the same in-flight `prepare()`).

### Models & offline-first

First run downloads the models; both then prefer their on-disk cache and load **offline** when present:

- WhisperKit (STT) → `~/Library/Application Support/OpenWhisperer/models/huggingface` (~1.5 GB; `SpeechTranscriber` prefers the on-disk cache and loads offline when present). `ModelStorage.migrateWhisperHubIfNeeded()` moves a legacy `~/Documents/huggingface` hub there at launch, before the model loads, so an existing cache isn't re-downloaded. The Parakeet models left behind by the reverted engine (`~/Library/Application Support/FluidAudio/Models`) are orphaned — `ModelStorage.locations` still lists them so Settings → Advanced → "Delete models" reclaims the space.
- FluidAudio Kokoro → `~/.cache/fluidaudio` (models and voice packs). **Not** relocated with Whisper: `KokoroAneManager` takes a custom `directory:`, but FluidAudio pins the shared G2P/English-lexicon assets to `~/.cache/fluidaudio` regardless (a `G2PModel.shared` singleton, `directory: nil` upstream), so moving only the model store would split the cache and risk breaking TTS. It's a hidden cache outside iCloud/Documents, so it stays put.
  - **Supertonic-3** (multilingual TTS) → also `~/.cache/fluidaudio/Models/supertonic-3` (~264 MB with the int8 VectorEstimator: ~70 MB core + one variant set; only the selected variant downloads). Fetched **on demand**, the first time a `supertonic:*` voice is used — an English-only user never downloads it, and `TTSEngines.prepare()` only pre-warms it when the selected voice routes there. Note FluidAudio's docs quote 398 MB; that counts *every* VectorEstimator variant.
  - *Note on Alternative Voices:* The upstream `FluidInference/kokoro-82m-coreml` repository only hosts the default `af_heart.bin` voice file under the `ANE/` subpath. Downloading alternative voices from this repository will fail (404/silent error). The Settings → Voice picker offers the full Kokoro-82M v1.0 roster (~54 voices, grouped by language); selecting any non-default voice triggers `KokoroTTS.ensureVoicePack`, which downloads its `<voice>.bin` from the `onnx-community/Kokoro-82M-v1.0-ONNX` repository (`resolve/main/voices/<voice>.bin`) into `~/.cache/fluidaudio/Models/kokoro-82m-coreml/ANE/<voice>.bin` on demand. It re-fetches if the cached file is missing or under 1 KB, and rejects non-200 responses so an error page is never cached as a voice.

This matters because the developer's firewall (Little Snitch) blocks the HuggingFace **Xet CDN**, which breaks fresh downloads — an already-cached model still loads.

## Conventions & gotchas

- **Code signing identity** is set by `OW_SIGN_IDENTITY` (default `-` = ad-hoc). With ad-hoc, the cdhash changes every build, so macOS **drops the Accessibility and Microphone grants** — dictation breaks until you remove and re-add the app in System Settings → Privacy & Security. **To stop the churn locally:** sign with a stable self-signed cert — `OW_SIGN_IDENTITY="OpenWhisperer Dev" ./build-dmg.sh` — whose designated requirement pins to the cert leaf hash (constant across rebuilds), so TCC grants persist; you re-grant only once. Release builds set `OW_SIGN_IDENTITY="Developer ID Application: …"` plus `OW_NOTARIZE=1` and `OW_NOTARIZE_PROFILE` to add hardened runtime (`Resources/OpenWhisperer.entitlements`) + notarize + staple the DMG (needs a paid Apple Developer account).
- Platform (Claude Code, Codex CLI, Pi, or Antigravity) is selected in Settings → Agents; `ConfigManager` applies the right thing per platform: Claude → hook in `~/.claude/settings.json` + `speak` MCP server in `~/.claude.json`; Codex → `speak` MCP server in `~/.codex/config.toml` + hook in `~/.codex/hooks.json` (needs one-time hook-trust); Pi → copies the `pi/openwhisperer.ts` extension into `~/.pi/agent/extensions/`; Antigravity → global hook and mcp config.
- Version is single-sourced from `app/Resources/Info.plist` — and **version bumps are Perikles's call alone; agents never bump** (rule set 2026-07-20). When he does bump, `CFBundleVersion` + `CFBundleShortVersionString` move together; `build-dmg.sh` derives the DMG name from `CFBundleShortVersionString` via PlistBuddy.
- **One-shot migrations** live in `AppDelegate.applicationDidFinishLaunching` as a short ledger of `ConfigManager.migrate…()` / `ModelStorage.migrate…()` calls. Each checks for the old state, repairs it, and is a no-op otherwise, so running every launch costs one small file read. When one repairs a file the app writes on Connect (the Claude Stop hook, the Codex inline hook), it calls the same idempotent apply Connect uses, so there is one tested code path. **Prune at a major bump, one major behind:** at 3.0 drop the ones that repair pre-2.0 state, at 4.0 the 2.x-era ones, and add a release-note line ("upgrading from 1.x: install the last 2.x first") — that line is what makes the deletion safe, since DMG installs skip versions. Two entries are not migrations and stay: `migrateDefaultSTTLanguage()` writes a default that fresh installs need forever, and `removeLegacyOverlayLines()` is one unlink. Migrations of files the app doesn't own (Codex, Claude hooks) can also go the day the old shape becomes impossible upstream. Pruning rides on whichever bump Perikles makes; agents never trigger it.
- **Rebuilding & Installing locally:** Since hook files (`hooks/*.sh`) are bundled into the application resource path (`OpenWhisperer.app/Contents/Resources/hooks/`) during build, any hook changes require rebuilding the app (`./build-dmg.sh`). To install it locally, terminate any running app instance (`killall OpenWhisperer`), remove the old app (`rm -rf /Applications/OpenWhisperer.app`), and copy the fresh build (`cp -R app/.build/OpenWhisperer.app /Applications/`).
- `app/Tools/` (G2PParity, STTDiag, FluidTTSSpike) are local-only diagnostic spikes and are **gitignored**.
- Design docs and implementation plans live in `docs/superpowers/{specs,plans}/`, organized by phase (Phase 1 = STT port, Phase 2 = native TTS, Phase 3 = streaming TTS). Consult these for the rationale behind the Swift port.
